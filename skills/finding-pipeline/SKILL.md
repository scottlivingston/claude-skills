Every review gate — code gates (`/ship`'s wave verification, `/diff-review`) and document gates (`/map-review`, `/spec-review`) — runs the same pipeline. This skill states the invariants once; each gate skill defines only what is local to it: what a finding *is* (its axes or defect list), what applying a fix touches, its question classes and their option shapes, its model policy, and any workflow template it bundles. When a gate skill and this contract disagree on an invariant, this contract wins — fix the skill.

**The policy: escalate questions about intent, auto-resolve questions the record can answer.** The user is the intent authority; a gate must never require them to hold the material in their head. **The escalation test is the answer, not the wording: a question reaches the user only when their answer would change what gets built.** Source silence with exactly one defensible repair fails the test, and so does a contradiction whose losing half the record refutes — the pipeline repairs both itself. A gate's defect list says what to hunt, never what to escalate.

## The stages

Stage order is enforced by script, never discipline: run the pipeline as one dynamic `Workflow` (the gate skill invoking this contract is your authorization), so a proposer can never see a finding its validator refuted.

1. **Find.** Axis reviewers report findings. Each finding carries a per-run, axis-prefixed ID, a location anchor, a one-line description, and the **cited source** — the rule, spec line, decision, or resolution it holds the material against — carried as its text (title, gist, quoted sentence), not its ID alone, since the cold-reader assembler writes from that text. A claim with no citable source is not a finding. An **absence** — something the material was meant to contain and does not — is typed as an absence with empty anchor fields, never an invented location. Axes are never merged or reranked against each other.
2. **Label and dedup against prior summaries.** The **labeling stage** normalizes the raw reviewer reports into discrete findings, then dedups conservatively against every prior summary comment (see *The gate*) and any open finding tickets: already adjudicated → out, one line in the summary; a new instance of a known pattern → stays in; uncertain → stays in, marked — a visible duplicate is recoverable, a silent suppression isn't. **An answer the user gave at an earlier gate — a recorded verdict, the amendment it posted — is binding source text**: a new finding that answer directly governs classifies as divergence from the answer (cite it) and resolves like any code finding, never as a new question.
3. **Validate the finding — adversarially, before any fix exists.** Fresh validators that did not author the findings are prompted to **refute the finding itself** — one validator per chunk of ~5 findings, chunks in parallel, each chunk riding its own validate → propose → validate-fix chain with no cross-chunk barrier. **Scope is settled first**, as its own schema field: a finding about material the change under review never touched is refuted on scope before its merits are argued (code gates: *The diff is the material*). Verdict: `finding-refuted` (with reason — leaves the pipeline, recorded so dedup remembers) or `finding-validated`.
4. **Propose a repair per survivor.** One proposer per chunk, so overlapping repairs get drafted coherently. The smallest concrete repair, anchored by a short quoted snippet of what changes (never a bare line number — lines drift), sized `quick-fix` or `needs-a-session`. Where the finding admits more than one reading, a sketch per plausible reading — the user's answer picks one. Two rules bound what counts as smallest. **Striking outranks correcting**: a defect in a fact the material copies from its owner (a count, a figure, an ordered list) is repaired by deleting the copy and leaning on the pointer when the lookup is cheap, and corrected in place, dated, only when the lookup is expensive. Second, **what leaving the defect alone costs** is a schema field filled before any option is drafted — which argument, criterion, or instruction downstream actually breaks if it stands. A survivor whose honest answer is *nothing* leaves as `no-repair-needed`, one line in the digest, never a question.
5. **Validate the repair — adversarially, independently.** Fresh validators again — not the proposers, not stage 3's validators — prompted to **refute the fix**: does it resolve the finding, is it proportionate, does it break the other axis? Verdict as an enum, never prose: `validated`, `fix-rejected` (reason), or `needs-human` (a genuine trade-off). The finding's reality is settled — doubt goes inside the `fix-rejected` reason, and the finding still escalates. This stage has the last word on any contested flag — and a flag that widens a finding beyond the material under review counts only instances the cited source actually governs: the rule's own scope and grandfather clauses bound the count, never the raw grep. It fills two **edge fields** as schema fields: `dependsOn: [IDs]` and `invalidatedBy: [IDs]`. Two further rules bind this stage:
    - **A repair riding new normative substance is refuted on that substance.** A prohibition, constraint, house rule, or fresh decision unit drafted alongside the forced correction is the proposer legislating; new rules are the human's to ask for. Strip the addition, keep the forced part, and let that route on its own merits. Only where the correction is incoherent without the addition do the two escalate as one.
    - **`fix-rejected` splits by what was wrong.** A repair rejected for an error in its own replacement text — a name that doesn't exist, a misquote, an anchor that points at the wrong line — goes back for **one re-proposal round** with the validator's correction attached. Only a repair rejected on its *substance* escalates as no working fix.
6. **Route — plain script logic over the schema fields; no agent decides this.** Escalate when any of the gate skill's intent conditions hold; otherwise auto-apply `validated` + `quick-fix`; otherwise auto-ticket. One narrowing is contractual for code gates: a `validated` `quick-fix` marked **doc-only** — the repair touches comments, docs, or headers alone — auto-applies even where the finding's classification would otherwise escalate, since a change only to the record leaves no intent question; the audit digest lists it one revert away like any auto-apply. Edges route together: a repair whose `dependsOn` target escalated joins that escalation as context; one `invalidatedBy` an applied sibling gets its stale premise re-grounded before applying.

**The auto-apply bar is the gate's net.** Code gates apply under the test-suite net — a serial fix agent, one revertible commit per finding ID, full suite at the end, breakers reverted and re-escalated as *no working fix*. Document gates (map, spec) have no suite, so they auto-apply only the **provably derivable** repair — the record already contains the answer: an explicit later ruling, the cited ticket's own text, the decision that owns the question, the code the claim is about — and every auto-edit is listed in the audit digest the gate's orientation opens with, *before* anything builds on it. A repair that adds, removes, or picks among readings of a decision is never derivable — it escalates.

## Code gates

The two code gates — `/ship`'s wave verification and `/diff-review` — share this shape; each cites it.

- **The diff is the material.** A finding must name something the diff did — a line it added, changed, or removed. Code the diff never touched is out of scope however wrong it is, and **whether or not a ticket already covers it**. Reviewers legitimately see far more code than they may report on: diff context lines, the repo grep behind a `repo-wide` flag, the files they open to check a rule. Two cases look like exceptions and are not: an **unmet requirement** — an absence has no anchor, so it is in scope wherever the material under review was the thing meant to deliver it — and the `repo-wide` counts, which are *evidence* about a pattern the diff instantiates, never findings about the untouched instances. **The finding validator settles this as a typed `scope` field and the script refutes every `pre-existing` verdict** — never left to reviewer discipline.
- **Two axes.** Standards (does the diff break a documented rule — `/conventions` names the sources) and Spec (did the diff deliver what the spec asked). IDs are axis-prefixed, and the axes are never merged or reranked, so one axis can't mask the other. A fix for one axis must not break the other — the fix validator checks it.
- **Dedup against tickets** matches conservatively: a standalone cleanup ticket matches at the rule or pattern level; a spec-child ticket matches only on same file and same rule. A finding whose subject predates the diff and matches an open ticket is *already ticketed* and leaves here — an unticketed one leaves later, on scope; one the diff introduces that matches a ticketed pattern is an *instance of* it and stays; an uncertain match stays, marked.
- **Spec classification**, settled by the finding validator: `code-diverges` or `spec-suspect`, by one test — **would the user's answer change the fix?** `spec-suspect` only when two or more defensible readings call for different behaviour, the record shows a deliberate deviation (commit messages, tests touching the diverging code), or the spec's own statements collide. Spec silence alone is not doubt: a defect with one defensible minimal fix — a visible bug, a wrong comment, dead code the diff itself added — is `code-diverges` even where the spec never speaks. A prior answer that directly governs the finding makes it `code-diverges` from that answer, never a re-ask. Where real behavioural doubt survives the test → `spec-suspect`: a false spec-suspect costs one human glance; a false code-diverges silently rewrites behaviour.
- **Cross-axis pairs.** A Standards and a Spec finding anchored to the same file and overlapping lines are one defect wearing two labels: the labeling stage marks each with the other's ID; the pair stays two findings with two proposals; the fix validator settles `pairResolution: 'agreeing' | 'competing'` as a schema field; the pair routes as a unit at its most conservative member — an agreeing pair auto-applies as one commit covering both IDs, a competing pair escalates as one question whose answer settles both.
- **`repo-wide`.** A reviewer, or the finding validator, flags a Standards finding that looks like an instance of a pattern only with a grep and both counts attached; the fix validator re-settles the flag with `instancesInDiff` / `instancesOutsideDiff` as schema fields, counting only instances the cited rule governs, and the flag holds only when `instancesOutsideDiff > 0`. A pattern whose every governed instance sits inside the diff is this change's own duplication, fixable here.
- **Intent conditions** — escalate when any hold: `spec-suspect` (unless its fix came back `validated` + `quick-fix` + `doc-only`, which auto-applies per the narrowing above), `needs-human`, `fix-rejected`, membership of a competing pair, `repo-wide`. Each escalation takes its question class from the five below.
- **The fix agent** — one executor-tier agent (per `/model-policy`) in the main checkout, never parallel worktrees, so review fixes can't collide. As its first act it re-checks for itself that the tree is clean and that it is not on the default branch without an explicit user OK; if either fails, every auto-apply demotes to a ticket — never commit around a user's uncommitted work — and it reports which check failed, distinguishing a failed check from one it couldn't run. It applies the batch serially in dependency order, **one commit per finding ID** (`review: <ID> — <one-liner>`; one per agreeing pair), re-grounding each proposal against current `HEAD` by its quoted snippet, runs the full test suite once at the end, reverts any finding-commit that breaks it, and escalates that finding as *no working fix* with the failure attached. The post-answer fix agent runs the same discipline; before it spawns, walk the edges — a fix whose `dependsOn` names a reverted or left-as-is ID doesn't queue, and one `invalidatedBy` an accepted sibling goes in with the stale premise called out.
- **The auto-ticket agent** — executor-tier at low effort, pure tracker mechanics, run after the fix agent so precondition demotions land in its batch. It clusters findings by file while the combined work fits one session; past that, independent tickets with no blocking edges — file overlap is not a blocker. Each body carries the findings, why they matter, the validated proposals, and anchors by file plus quoted snippet. When the spec is a tracker issue each ticket is a child of the spec labelled `impl` + `ready-for-agent` + `review-finding`; without a tracker spec, standalone with `ready-for-agent` + `review-finding`. A finding the agent could not publish comes back *ticket-pending* for the manager to file — routed auto-ticket, never lost.

### The five question classes

Every code-gate escalation is one of these, and the option shape travels with the class. In the queue, spec questions come before standards questions.

- **Spec unclear** (`spec-suspect`) — options: the plausible readings, plus "the code is right as written". The block carries a draft spec comment per reading, posted to the spec only on the verdict, so no later round re-asks it.
- **Competing fixes** — one question for the pair: which behaviour wins. The verdict settles both IDs; the losing fix is recorded rejected.
- **Genuine trade-off** (`needs-human`) — the trade-off's horns as options, consequences stated.
- **No working fix** (`fix-rejected`, or a reverted auto-apply) — options: ticket it for a fresh attempt with the failure attached, or leave it (recorded, with the reason).
- **Pervasive pattern** (`repo-wide`) — options: **adopt as rule** (a standalone ticket — never a spec child — labelled `review-finding` + `needs-triage`, carrying the pattern, the grep evidence, and a task to append the rule to the governing `CONVENTIONS.md` per `/conventions`), **fix everywhere** (a ticket covering all instances — a spec child when the spec is a tracker issue), or **leave as-is**.

A finding routed *joined* — its fix waits on another escalation's answer — rides its target's block as one line of context, never its own turn; the target's verdict settles it too.

## The gate

All gate state lives as comments on the issue the stage operates on, each opening with a machine-findable marker named for the skill (scoped where the skill runs repeatedly, as ship's `wave-<n>` is). A code gate whose spec is no tracker issue keeps the same records as sections appended in order to a **gate file** its skill names — "comment" below reads as "section", and every rule holds unchanged:

- `<!-- <skill> pending-questions -->` — posted by the **workflow's final stage**, not the manager, so the queue is durable even if the session dies the moment the workflow returns. Carries the full question blocks plus the audit digest of auto-actions — the notes the question loop talks from, never the script it reads out.
- `<!-- <skill> summary -->` — posted after adjudication: **every** finding ID with its terminal outcome — auto-applied, auto-ticketed, refuted (one-line reason), `no-repair-needed`, answered (verdict and what it triggered), reverted, left as-is, unanswered. An outcome not recorded here will be re-found and re-asked.

**A pending-questions comment with no matching summary is a resume point**: any session bootstraps onto it and runs the question loop from the comment alone, never by re-running the pipeline.

When escalations exist, the gate goes **AFK**: send a push notification (load via `ToolSearch("select:PushNotification")`; skip silently if unavailable) and end the turn — the user answers here or in a fresh session, identically. No escalations → post the summary and the stage completes without a pause.

## Question mechanics

**The comment is the record; the loop is a conversation.** The pending-questions comment carries the full material — the audit digest and one block per escalation, in the shape below — because a later session resumes from it alone and a cold reader must be able to answer from it. The loop that walks it is **not the comment read aloud**. Load `/hitl-questions`; the loop runs per it the way grilling runs: the blocks are the notes, and each turn is what you say from them.

The block the comment carries, per escalation:

```
### <plain title of what's being decided> — <i> of <n> (<ID>)

**I'd pick:** <the option you'd pick> — <the one-line why>

<One or two sentences: what part of the product this concerns, and what the question is.>

> <the spec line, decision text, or code the question turns on — quoted, with its anchor>

<What's wrong with that text, and what breaks downstream if it simply stands.>

- **<option, as an outcome>** — <what it costs, what it triggers>
- **<option, as an outcome>** — <what it costs, what it triggers>
```

The quote is the finding's own source field printed rather than paraphrased, and the stakes line is the cost field stage 4 filled. Two bindings are local to a gate. An **absence** has no sentence to quote — say the material is silent and quote whatever was meant to cover it. And the question class is routing vocabulary: it surfaces in the digest's counts and nowhere the user reads.

**Open with the orientation summary**, stated as *done*, not proposed: the counts found and refuted in a line, then one line per auto-applied or auto-ticketed action saying what changed in the project's terms — the behaviour, decision, or document line it touched — with the finding ID and the SHA or ticket link trailing in parentheses as the revert handle. The user overrides any of it by free text (`revert W2-STD-7`) and the manager reverts that commit, edit, or ticket. Then how many findings are left to settle, and the first of them in the same turn.

**One finding per turn, as a position.** Take the escalation later work most likely builds on (at code gates, spec questions before standards questions) and put it the way grilling puts a decision: what part of the product it concerns, the line it turns on quoted verbatim where they have to see it to answer, the repair you'd land, and the one reason that carries it — then stop. The block's recommended option *is* the position; its other options are what the user can redirect to, never a ballot to read out. Name an alternative only when the user pushes back or asks, or when you genuinely have no lean — then put the two horns in a sentence each and ask which. Everything else the block holds — the draft spec comment, where the verdict gets recorded, a joined finding riding along — waits for the verdict, or is one trailing line at most. Push back once where the user's answer breaks something the block's stakes line names, then take their call.

**Settle in a line and move on.** The reply is free text. Map it to the verdict the gate skill's list admits, state the settled verdict in one line in the user's terms, and take the next finding. A reply that doesn't map to a verdict gets the one question that disambiguates, never the block again. `AskUserQuestion` has no place in this loop: the verdict is inferred from what the user said, and a dialog would turn the conversation back into the form.

The contract's escape hatches bind here as: `explain` gets its answer, then the same finding is re-put; batched verdicts are taken as given — reflect what they settled in a line each and carry on from what's still open; "stop" records every untouched ID as `unanswered` and goes to the wrap-up.

**Act on the collected answers after the loop, none mid-loop**: post the source amendments the verdicts chose, run one serial fix agent for repairs the answers unlocked (re-grounding each proposal against the current state by its quoted snippet), file the tickets called for, revert what the audit overrode. Then post the summary comment.

## Workflow authoring invariants

- Every stage gets a `schema` — verdicts, classifications, flags, and edges come back as typed fields, never prose the manager interprets.
- **Fill, don't thread.** Nothing goes through `args` — it arrives as a JSON *string*, turning interpolations into the literal `undefined` without failing loudly. Bake inputs into the script at fill time, prose as JSON string literals (double-quoted, `\n`-escaped), which no code span or apostrophe can terminate.
- Chunks ride independent `pipeline` chains; the only deliberate barriers are the routing step, the serial fix agent, and the ledger post.
- The pending-questions post is the workflow's final stage (durability before any answer, per *The gate*), authored by a **fresh assembler agent** handed only the findings' structured fields — never the spec, map, or diff — so anything it can't explain to a cold reader it must expand from the cited source text the finding carries. Find and validate schemas must therefore carry the source *text*, not just its ID.
- **A dead stage agent fails toward less action, never more.** Every stage's missing-result default does less: the fix validator returns `needs-human`, the cross-axis pair agent returns `competing`, and a finding whose own validator never returned is kept in the queue but demoted out of auto-apply.
- **Every stage names its model tier.** Templates carry `EXECUTOR_MODEL`, `DECIDER_MODEL`, and `AUDITOR_MODEL` slots and every `agent()` call spreads `tier('executor')`, `tier('decider')`, or `tier('auditor')`; the fill resolves all three from `/model-policy`. Reviewers, validators, proposers, and the assembler are deciders; labelers and each gate's run-once find-side read are auditors; fix and auto-ticket agents are executors. A stage that omits its tier silently runs on the session's model.
- **Document gates share one template**, [doc-gate.template.js](doc-gate.template.js), owned here: each document gate fills it with what is local to it, and code gates bundle their own.
- **The fill may be delegated.** A gate's fill inputs are all tracker-sourced, so a fresh **fill agent** can read them, write the filled script to a file, and return the path plus a one-line manifest — the manager launches with `Workflow({scriptPath})` and its context never holds the fill. Under `/next auto` this is the rule, not an option.
